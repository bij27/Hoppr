# Hoppr

Find live happy hours in Fort Lauderdale and plan a bar crawl that hits each one while it's on.
iOS, Android, and web from one Expo codebase.

## Run it

```bash
npm install
npm run web        # browser
npm start          # then scan the QR code with Expo Go on your phone
```

## Checks (run before every merge)

```bash
npm test           # unit tests: schedules, DST, overnight deals, crawl planner
npm run typecheck
npx expo lint
```

## Layout

| Path | What's there |
|---|---|
| `src/app/` | Screens (Expo Router). `index.tsx` = map home with the pull-up list, `crawl.tsx` = crawl planner, `venue/[id].tsx` = venue page |
| `src/components/` | UI pieces. `map/` (react-native-maps on iOS/Android, Leaflet on web), `bottom-sheet.tsx` |
| `src/constants/theme.ts` | Design tokens ("ink & amber" colors, spacing, radius). Add colors here, not in screens |
| `src/lib/` | Core logic, no UI. `time.ts` (timezone-aware deal windows), `crawl.ts` (route planner), `feed.ts` (home filtering/ranking), `deals.ts`, `format.ts`, `geo.ts` |
| `src/data/` | Data access. `venues.ts` is the only place screens get venue data from |
| `src/state/` | App-wide state (loaded venues, current crawl) |
| `supabase/migrations/` | Database schema (Postgres + PostGIS) |

## How deal times work

Times are stored as the bar's local wall-clock minutes (`960` = 4 PM). A deal like
"Fri 11 PM – 2 AM" is stored on Friday with `start=1380, end=120`; the app treats an end at or
before the start as running past midnight. Daylight saving is handled; see `src/lib/__tests__/time.test.ts`.

## Data

The app reads venues from Supabase through the `get_venues()` database function
(`src/data/venues.ts` → `src/lib/supabase.ts`). Copy `.env.example` to `.env` and fill in the
project URL and publishable key.

In development, if the database has no published venues yet (or `.env` is missing), the app shows
the **fictional sample bars** in `src/data/fixtures.ts`. Production builds never show them.

Schema changes live in `supabase/migrations/`. Each new file must be run once against the
database, in filename order (currently by pasting it into the Supabase SQL Editor).

## Adding bars from the scouting sheet

Fill in the Google Sheet (Bars, Deals, Menus tabs), download each tab as CSV, then run
`npm run import-sheet -- ~/Downloads`. It writes a SQL file in `supabase/venues/` to run in the
SQL Editor. Full guide and column reference: `supabase/sheet-template/README.md`.

## Tags, events and filters

- Tags live in `src/constants/tags.json` (one list for the app and the sheet importer). Bars get
  feature tags (pool, patio…); deals and events get night tags (karaoke, ladies night…).
- A listing is a deal (`kind = 'deal'`) or an event (`kind = 'event'`, e.g. live music with no
  discount). Events use the same days/times as deals.
- Home filters: OR within a group, AND across groups. With an event or deal-type filter, the time
  tab applies to the matching listings (Live now + Karaoke = karaoke on now). Logic:
  `viewVenue()` in `src/lib/feed.ts`.
- Colors stay about deals. While an event is on, the bar shows an ink badge ("Live music now") and,
  if no deal is on, an ink map pin.

## Brand

The leaping frog is generated by `scripts/brand/generate.mjs` (`npm run brand`), which writes
`src/components/frog-paths.ts` and renders the icon, Android icon layers, splash images and
favicon. Change the shape there, never by editing the PNGs.

- The native splash is a static green frog. When the app starts, `LaunchScreen` takes over at
  the same spot: the frog crouches and hops red → orange → green (the deal status colors), then
  fades once the venues load. `FrogLoader` is the looping version, used for loading states.
- Expo Go shows neither the custom icon nor the splash; check those in a preview/production build.

## First launch, privacy and saved data

- `AgeGate` asks "Are you 21 or older?" once; a yes is remembered on the device.
- The privacy policy is `src/app/privacy.tsx`. Keep it true to what the app does, and update
  `PRIVACY_EFFECTIVE_DATE` in `src/constants/app.ts` when it changes. Set
  `PRIVACY_CONTACT_EMAIL` there before submitting to the App Store.
- The crawl being planned is saved on the device (`useStoredValue`, `src/lib/kv.ts`).

## Community feedback

Each deal has **Still on? → ✓ Yes** (offered only while the deal is live) and **Something's off?**
(choose a reason, add an optional note). People don't need an account: the first time they tap one,
the app signs them in anonymously with Supabase (Authentication → Sign In / Providers → *Allow
anonymous sign-ins* must be on). Later, Apple and Google sign-in will upgrade that same account.

- Each person can confirm and report a deal once per day (enforced in the database).
- Deals show "Confirmed by N people this week" when anyone has confirmed them, and otherwise the
  admin "Verified …" date.
- Reports go to the admins only and never change a listing automatically. To review them, run
  `supabase/admin/open_reports.sql` in the SQL Editor (it includes resolve and turn-off snippets).
- **Suggest a bar or deal**: from the bottom of the home list ("Know a happy hour we're missing?")
  or a venue page ("Know another deal here?"). Anyone can send one (up to 5 a day), and it stays
  private until an admin adds it. Review them with `supabase/admin/suggestions.sql`.
- Social features (sharing, friends, group crawls) will require a real account. Crawls stay private
  and invite-only.

## Maps

- iOS uses Apple Maps and needs no key. Android uses Google Maps: it works in Expo Go, but store
  builds need a Google Maps API key (react-native-maps config plugin, `androidGoogleMapsApiKey`).
- Web uses Leaflet with OpenStreetMap's tile servers, tinted grayscale in CSS. That's fine for
  development, but OSM's servers aren't for app traffic: switch to a keyed tile provider
  (e.g. Stadia Maps or MapTiler) before a public launch.
